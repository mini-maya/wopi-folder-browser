== Ziel und Scope

Diese Dokumentation beschreibt die aktuelle Zielarchitektur mit Multi-Storage-Unterstuetzung
(`documents` + `external`) und einer provider-faehigen Storage-Schicht.

Fokus:

* klare Trennung von UI, API, WOPI und Storage
* eindeutige Dokument-Identitaet pro Storage
* sichere Pfadauflosung (Traversal/Symlink-Schutz)
* Read-only- und Availability-Verhalten
* Erweiterbarkeit fuer weitere Provider (WebDAV/SMB/S3)

== Storage-Modell

Beispiel-Konfiguration (persistiert in `WOPI_STATE_ROOT/common/storages.json`):

[source,json]
----
{
  "storages": [
    {
      "id": "documents",
      "name": "Documents",
      "type": "local",
      "root": "/documents",
      "enabled": true,
      "readOnly": false,
      "system": true
    },
    {
      "id": "external",
      "name": "External Storage",
      "type": "local",
      "root": "/external/storage",
      "enabled": true,
      "readOnly": false,
      "system": false
    }
  ]
}
----

Wichtige Regeln:

* `id` ist stabil und technisch relevant.
* `name` ist reine Darstellung.
* `root` ist immer Container-Pfad, nie Host-Pfad.
* `enabled=false` deaktiviert Storage zur Laufzeit.
* `readOnly=true` sperrt mutierende Operationen.

== Startup und Registry/Health-Flow

[plantuml, startup-health, svg]
....
@startuml
skinparam shadowing false

start
:App start;
:StorageManager.initialize();
:load/create storages.json;

repeat
  :for each enabled storage;
  :instantiate provider;
  :healthCheck (exists/dir/read/write);
  if (healthy?) then (yes)
    :mark available=true;
    :log "[storage] <id>: OK";
  else (no)
    :mark available=false;
    :log unavailable reason;
  endif
repeat while (more storages?) is (yes)

:ready to serve requests;
stop
@enduml
....

== Request-Routing und Storage-Auswahl

Storage wird bestimmt ueber:

1. URL-Praefix `/storage/<id>`
2. Header `X-Storage-Id`
3. Query `storageId`
4. Session `selectedStorageId`
5. Fallback `documents`

[plantuml, request-storage-resolution, svg]
....
@startuml
skinparam shadowing false
start
:incoming request;
if (path starts with /storage/<id>?) then (yes)
  :use id from path;
elseif (X-Storage-Id present?) then (yes)
  :use id from header;
elseif (query storageId present?) then (yes)
  :use id from query;
elseif (session selectedStorageId?) then (yes)
  :use id from session;
else (fallback)
  :use documents;
endif

:StorageManager.resolveOrHttpError(id);
if (available?) then (yes)
  :attach req.storage;
else (no)
  :API/WOPI -> error;
  :UI routes -> safe fallback;
endif
stop
@enduml
....

  listet Storage-Metadaten ohne interne `root`-Pfade.

* `GET /api/admin/external-acl` +
  liefert die aktuelle `allowedUserIds`-Liste fuer den External-Storage.
* `POST /api/admin/external-acl` +
  aktualisiert die External-Storage-Allowlist.

== Sicherheitsarchitektur

== Sicherheitsarchitektur

=== Access Control Matrix

Die Anwendung implementiert ein rollenbasiertes Zugriffskontrollsystem mit vier Speichertypen:

[cols="1,2,2,2,2", options="header"]
|====
| Storage | Anonym | Auth User | Admin | Hinweise
| `documents` | ❌ | ✅ User-scoped | ✅ | Per-Benutzer Isolation in `/documents/users/<userId>/`
| `shared` | Mode-abhängig | Mode-abhängig | ✅ | Konfigurierbar: disabled/auth/readonly/readwrite
| `external` | ❌ | ACL-abhängig | ✅ | Leere ACL = alle auth User; gefüllte ACL = nur Whitelist
| `recycle` | ❌ | ✅ Same user | ✅ | Pro-Benutzer Recycle-Bin
|====

=== Shared Storage Modus (Konfigurierbar)

Die `shared`-Storage wird durch `SHARED_STORAGE_MODE` konfiguriert:

* `disabled` (Standard): nicht sichtbar, nicht zugänglich
* `auth`: sichtbar nur für authentifizierte Benutzer, read-write
* `readonly`: sichtbar für alle (auch anonym), nur Lesen
* `readwrite`: sichtbar für alle (auch anonym), read-write

=== Per-Benutzer Document Root Isolation

Authentifizierte Benutzer erhalten automatisch einen isolierten Dokumentenroot:

----
Host:    /srv/wopi/documents/
         └─ user1/
         └─ user2/

Container: /documents/users/
           └─ <user-id-1>/    (nur User 1 sieht diesen Inhalt)
           └─ <user-id-2>/    (nur User 2 sieht diesen Inhalt)
----

Nichtauthentifizierte Anfragen/Freigaben verwenden einen gemeinsamen root: `/documents/shared`

=== External Storage ACL

`external`-Storage wird mit `allowedUserIds` konfiguriert (persistent in `storages.json`):

* Leere ACL: Alle authentifizierten Benutzer können zugreifen
* Gefüllte ACL: Nur in der Liste enthaltene Benutzer-IDs können zugreifen
* Nichtauthentifizierte Benutzer: Immer abgelehnt (403)

Verwaltung über `/api/admin/external-acl`:
----
GET /api/admin/external-acl
    → { "allowedUserIds": ["alice", "bob"] }

POST /api/admin/external-acl
    → { "allowedUserIds": ["alice"] }
    → Persisted in storages.json
----

=== Pfadsicherheit

Zentrale Regeln in `lib/storage/storagePath.js`:

* nur relative Pfade
* keine absoluten Pfade
* keine `.` / `..`-Traversal-Segmente
* Backslashes werden normalisiert und validiert
* Parent-`realpath`-Pruefung verhindert Symlink-Escape

[plantuml, path-security, svg]
....
@startuml
skinparam shadowing false
start
:input relativePath;
:normalize (/ + \\ handling);
if (absolute?) then (yes)
  :reject;
  stop
endif
if (contains . or .. segments?) then (yes)
  :reject;
  stop
endif
:resolve candidate under root;
if (candidate outside root?) then (yes)
  :reject;
  stop
endif
:realpath(existing parent);
if (parent outside root?) then (yes)
  :reject;
  stop
endif
:safe absolute path;
stop
@enduml
....

=== Read-only Enforcement

* Backend blockiert mutierende Operationen (API + WOPI).
* Provider blockiert write/delete/rename/copy/mkdir zusaetzlich zentral.
* UI deaktiviert mutierende Aktionen fuer read-only Storages.

== Operative Hinweise

* Fehlt `/external/storage`, bleibt die App lauffaehig; Storage wird als unavailable markiert.
* Host-Pfade werden nie ueber API/Frontend geleakt.
* Logging enthaelt Health-Status pro Storage beim Startup.
